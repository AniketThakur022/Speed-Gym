A stolen session token kills the whole device session

Refreshing issues a new token. Replaying the old one doesn't just fail — it revokes the session, so the freshly issued token dies too. An attacker holding a copied token gains nothing and the real user is logged out rather than silently shadowed.

replay old refresh → 401 refresh token replay detected; device session revoked use new refresh → 401 refresh token revoked

Offline work syncs once, even when the phone sends it twice

A batch of two events is accepted and scores XP. The byte-identical resend is accepted as zero, awards nothing, and the database still holds exactly two rows — verified directly in Postgres, not inferred from the API response.

Dark features answer 404, not 403

A feature that is switched off is indistinguishable from one that never existed. A 403 would confirm to anyone probing that something unreleased is there; 404 tells them nothing.

social_friends ON → 200 social_clips dark → 404

A forged payment signature never grants anything

Verified on a throwaway server so the shared one was never reconfigured: forged and tampered webhooks are rejected, a correctly signed one is accepted, and a redelivery of the same bytes is recognised as a duplicate — because the ledger key is a hash of the signed body, not the unsigned header a caller can freely change.

forged sig → 400 tampered body → 400 valid → 200 redelivery → duplicate

Prices are derived, not hardcoded

The pro tier is stored in USD cents and converted at the configured rate, so a rate change moves every price coherently instead of leaving stale rupee literals scattered in code.

600 US cents × 84.0 → 50,400 paise (₹504.00)
What did not work, stated plainly
  • The API process on :8000 is running stale code. It serves 30 routes; the current tree has 78. Six whole routers — dashboard, mocks, chat, billing, social, family — are missing from that process. The demo detected this and drove a current build instead rather than reporting a passing demo against an old server. Restart that uvicorn before showing anyone.
  • The audit caught the capture's own staleness. It reported 77 routes; a server booted from the current commit serves 78. The demo's chosen target was itself five hours behind HEAD — it failed the very test it had applied to :8000. No other number was affected; a fresh build returned byte-identical results for practice, billing and chat.
  • No real payment was attempted. Provider keys are absent, so checkout returns an honest 503 naming what is missing. Signature verification was proven separately.
  • CAT's −1 penalty could not be shown over HTTP — only the quant pool is bound, and it yields numeric answers, which correctly carry no penalty. The arithmetic was demonstrated by calling the real scoring engine directly: 10×(+3) + 6×(−1) + 8×0 = 24.0/72.0. Honest, but an engine call rather than a round trip.
  • No generated content is servable yet. Every factory item is quarantined pending the judge models, so the generated tier is empty in every session. The API reports this rather than hiding it.

Everything generated tonight is quarantined, by design

With no judge keys, the seventh stage votes “pending” for every item, so all 326 terminate in quarantine and none can be promoted. This is the safety property working, not an outage: content cannot reach a learner by default, only by passing.

A malformed verdict cannot smuggle content through

The intake refuses verdicts that don't survive scrutiny — a stated result that contradicts its own panel's votes, three identical reviewers dressed as a panel, an unattributable verdict with no backend named. The gate distrusts the paperwork, not just the content.

What did not work, stated plainly
  • The judge panel is key-blocked — no keys for the three configured models, so nothing can ever leave quarantine today. Every downstream “0 promoted” follows from this one fact.
  • The demo found a real gap in the auditor it was demonstrating. KaTeX has no metrics for the rupee sign, and the auditor's character lists omit it, so four formulas pass the render stage and still draw a wrong glyph. The renderer only warns on stderr, so nothing downstream can see it. Deliberately reported, not patched from inside a demo script.
  • The run's exact counts cannot be reproduced. Parameter sampling is random against a growing deduplication window; a re-run audited 950 and delivered 319. The mechanism is real and the run's own artefacts on disk carry precisely the reported figures.

The “before” number is reconstructed, not quoted

Rather than trusting the documented 68.5%, the demo replays every key ever added as a patch, checks which actually landed, and subtracts them. The reconstruction lands on 68.5% exactly — independently corroborating the figure — and produces the per-book recovery table as a by-product.

A fabricated answer is caught before it can be written

A corrupted patch was built with six injected faults, including an invented option list. The preservation gate compares proposed text against the cited page's own OCR and rejects it at a 90% off-page token rate. Exit code 1 means the apply step never runs.

fabricated row → 90.0% off-page tokens → REFUSED (exit 1) rewrite with no page citation → REFUSED: no preservation reference

Suspected errors are presented as evidence, not verdicts

Twenty-three answer keys where the book appears to disagree with our stored value are shown for review — including the admission that the largest cluster turned out to be our own method error rather than the book's. Nine were corrected after checking the page images, with the superseded value kept.

23 flagged for review → 9 corrected → 30 marked suspect → old values retained

Unknown is a state, distinct from decided

A topic that reviewers considered and rejected is not the same as one nobody has mapped. The export carries both separately, and a further flag marks which resolved topics can actually drive mastery tracking — so no fabricated identifier ever reaches the learning engine.
